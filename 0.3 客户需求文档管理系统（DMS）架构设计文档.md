## 一、文档概述

### 1.1 文档目的

本文档依据TOGAF®标准第10版架构开发方法（ADM），从业务架构、数据架构、应用架构和技术架构四个维度，系统阐述客户需求文档管理系统（DMS）的架构设计。

TOGAF是一种全面、开放的企业架构框架，其目的是帮助组织创造并管理其企业信息架构。本文档遵循TOGAF四大架构域（BDAT：Business、Data、Application、Technology）的方法论，完成DMS系统的架构设计。

### 1.2 业务场景

根据业务需求，技术部需要管理客户上传的需求文档：

> **场景描述**：技术部通过DMS系统管理客户需求文档。
> - **文档上传**：客户/技术部上传需求文档，包含3D模型、图片、文字描述等多种格式
> - **标签管理**：上传时需为需求打标签（tag），便于分类与检索
> - **智能分流**：系统根据标签（tag）自动将需求分流至对应的处理部门/人员

### 1.3 参考标准

- TOGAF®标准第10版
- 行业DMS架构设计最佳实践
- 企业客户主数据中心架构文档（C-MDM）
- CRM系统架构设计文档


## 二、业务架构（Business Architecture）

### 2.1 业务愿景与目标

客户需求文档管理系统建设的核心目标是：**建立统一的需求文档采集、分类、存储与分发平台，实现客户需求从上传到处理的全流程数字化管理**。

具体目标包括：
- 支持多格式需求文档的上传（3D模型、图片、文字描述等）
- 建立统一的标签体系，实现需求的精准分类
- 基于标签的智能分流机制，自动将需求推送至对应处理单元
- 实现需求文档的全生命周期管理（上传→审核→分发→处理→归档）
- 与C-MDM集成，关联客户信息

### 2.2 业务能力模型

DMS系统支撑的核心业务能力包括：

| 能力域         | 能力项          | 说明                                                         |
| -------------- | --------------- | ------------------------------------------------------------ |
| 文档采集       | 多格式文件上传  | 支持3D模型（.stl/.obj/.step等）、图片（.jpg/.png等）、文字描述 |
| 文档元数据管理 | 标签标注        | 上传时打标签，支持自定义标签与标签字典                       |
| 文档存储       | 统一存储管理    | 结构化存储元数据，分布式存储原始文件                         |
| 文档分类       | 智能分流        | 基于标签规则自动分流至对应部门/人员                          |
| 文档检索       | 全文检索        | 按标签、关键词、客户等多维度检索                             |
| 权限与安全     | 访问控制        | 基于角色的权限管理，操作审计追踪                             |
| 系统集成       | 与C-MDM/CRM集成 | 关联客户信息，形成闭环                                       |

### 2.3 利益相关者分析

| 利益相关者     | 角色与职责                       |
| -------------- | -------------------------------- |
| 技术部         | 需求文档的接收、审核、分发与处理 |

| 接单部         | 客户信息维护（通过C-MDM）        |

| 数据治理委员会 | 制定标签标准与数据治理规则       |

## 三、数据架构（Data Architecture）

### 3.1 数据架构目标

TOGAF数据架构的核心是定义企业数据的分类、数据模型、数据存储、数据流、数据质量等。DMS数据架构需定义需求文档的元数据模型、物理存储方案及数据流向。

构建功能完整、高内聚低耦合的DMS应用平台。核心设计原则：

## 五、技术架构（Technology Architecture）

### 5.1 技术架构原则

- **高可用性**：需求文档为重要业务数据，需保障服务可用性
- **可扩展性**：支持文档数量的线性增长
- **多格式支持**：支持3D模型、图片、文档等多种格式
- **安全性**：需求文档涉及客户商业信息，需严格安全管控

### 5.2 分层架构设计

### 5.4 文件存储方案

采用**元数据与文件分离**的存储架构：

| 存储类型     | 存储内容                                   | 技术方案                 |
| ------------ | ------------------------------------------ | ------------------------ |
| 结构化存储   | 文档元数据（文档ID、标签、客户ID、描述等） | MySQL/PostgreSQL         |
| 非结构化存储 | 原始文件（3D模型、图片、文档等）           | 对象存储（OSS/S3/MinIO） |
| 索引存储     | 全文检索索引                               | Elasticsearch            |

**文件存储策略**：
- 大文件（>10MB）直接存储至对象存储，数据库仅保存路径
- 小文件可Base64编码后与元数据一并存储
- 开启对象存储的版本控制功能，实现文档版本管理

## 六、与C-MDM/CRM的集成设计

### 6.1 集成原则

| 原则               | 说明                                            |
| ------------------ | ----------------------------------------------- |
| 客户主数据单向引用 | C-MDM为唯一客户数据源，DMS只读消费              |
| 文档信息可回传     | DMS中的需求文档信息可回传至CRM，丰富客户360视图 |
| 实时优先           | 客户信息变更实时同步                            |
| 异步解耦           | 文档上传、分流等操作通过消息队列异步处理        |

### 6.2 集成架构

```
    ┌──────────────────────────────────────────────────────────────┐
    │                    集成方案                                  │
    ├──────────────────────────────────────────────────────────────┤
    │  与C-MDM集成：                                              │
    │  · 上传需求时，通过customer_id关联客户主数据                 │
    │  · 客户信息变更实时同步至DMS                                │
    ├──────────────────────────────────────────────────────────────┤
    │  与CRM集成：                                                │
    │  · 需求文档信息回传至CRM，关联至客户360视图                  │
    │  · 销售可通过CRM查看客户的历史需求文档                      │
    ├──────────────────────────────────────────────────────────────┤
    │  与消息通知集成：                                           │
    │  · 分流后自动推送通知至处理人                              │
    │  · 需求状态变更通知相关方                                  │
    └──────────────────────────────────────────────────────────────┘
```

### 6.3 数据映射

| DMS字段       | 来源系统  | 映射字段                  |
| ------------- | --------- | ------------------------- |
| customer_id   | C-MDM     | customer_id               |
| customer_name | C-MDM     | customer_name             |
| contact_phone | C-MDM     | phone                     |
| 需求文档信息  | DMS → CRM | 作为客户附件/需求记录同步 |


## 七、安全与权限设计

### 7.1 权限模型

采用RBAC（基于角色的访问控制）模型：

| 角色       | 权限范围                               |
| ---------- | -------------------------------------- |
| 客户       | 上传需求文档、查看自己上传的文档状态   |
| 技术部专员 | 上传、查看、处理分配的需求文档         |
| 技术部主管 | 查看全部需求、审核分流规则、报表查看   |
| 管理员     | 系统配置、用户管理、标签管理、审计日志 |
| 销售       | 通过CRM查看客户关联的需求文档（只读）  |

### 7.2 安全措施

- **传输加密**：全链路HTTPS加密
- **存储加密**：敏感文档加密存储
- **操作审计**：上传、下载、删除、分流等关键操作全记录
- **访问控制**：基于角色的细粒度权限控制
- **水印与防泄漏**：重要文档支持水印预览

## 九、风险与应对

| 风险                       | 影响         | 应对措施                               |
| -------------------------- | ------------ | -------------------------------------- |
| 3D模型文件过大影响上传性能 | 用户体验差   | 采用分片上传、断点续传；大文件异步处理 |
| 标签体系混乱导致分流不准   | 需求处理错误 | 建立标签字典，标签审核机制             |
| 文档存储容量快速增长       | 成本失控     | 制定存储生命周期策略，冷热分层         |
| 客户数据安全合规风险       | 法律风险     | 严格权限管控，操作审计，数据加密       |
